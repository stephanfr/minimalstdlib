# AArch64 litmus tests for the library's seq_cst fences

TLA+ models are sequentially consistent, so they cannot show whether the code is correct on AArch64's weaker memory
model. These tests check the three places where correctness depends on a `__atomic_thread_fence(__ATOMIC_SEQ_CST)`
(`dmb ish`). They use **herd7**, which enumerates every outcome the Arm architecture's own axiomatic model
(`aarch64.cat`) allows.

All three have the store-buffering shape: each side writes its own word, fences, then reads the other side's word. The
bug is the outcome in which both sides miss the other's write.

| Test | Code | Bad outcome (the `exists` clause) |
|------|------|-----------------------------------|
| `A-boundary-*` | `lockfree_single_arena_resource`: the frontier CAS, then the metadata count (`get_next_empty_memory_block`) vs. the count CAS, then the frontier (`grow_metadata_region`) | both claims succeed and neither sees the other: a block overlaps a metadata record |
| `B-upperlevels-*` | skiplist: `upper_levels_remaining_` `fetch_add`, then the inserter's own link vs. the remover's tombstone CAS, then `upper_levels_drained()` | the inserter publishes over an unmarked link while the remover sees no reservation and retires the node |
| `C-epoch-*` | `epoch_reclaimer_core` / `slot_policy`: `enter_read_section` (`reader_depth_` `fetch_add`, epoch store, fence), then a link load vs. an unlink CAS, then the reclaimer's `reader_depth_` load | the reader still sees the unlinked node while the reclaimer sees no reader and frees it |

Each comes in three code generations, taken from clang 18 `-O2` output for `probe.cpp` (the same atomic operations and
memory orders as the library), with and without the `DMB ISH`:

| Suffix | Codegen | RMW | Acquire load |
|--------|---------|-----|--------------|
| `a53` | `-mcpu=cortex-a53` (Armv8.0) | `LDAXR`/`STLXR` | `LDAR` |
| `a76` | `-mcpu=cortex-a76` (LSE, RCpc) | `CASAL` / `LDADDAL` | `LDAPR` |
| `llsc-rcpc` | `-mcpu=generic+rcpc`, `cortex-a55+nolse`, `cortex-a76+nolse` | `LDAXR`/`STLXR` | `LDAPR` |

Locations are 32-bit in the tests (herd7 rejects mixed sizes); only the ordering matters.

## Results (herdtools7 7.58+1, `aarch64.cat`)

| Test | with `DMB ISH` (the code) | without |
|------|---------------------------|---------|
| `A-boundary` a53 / a76 / llsc-rcpc | Never / Never / Never | Never / Never / **Sometimes** |
| `B-upperlevels` a53 / a76 / llsc-rcpc | Never / Never / Never | Never / Never / **Sometimes** |
| `C-epoch` a53 / a76 / llsc-rcpc | Never / Never / Never | Never / Never / **Sometimes** |
| `SB` / `SB+dmbs` (sanity check) | Never | Sometimes |

- With the fences the bad outcome is impossible for every codegen.
- Without them it is still impossible for the `a53` and `a76` codegens: a release write followed by an `LDAR` is
  ordered (RCsc), and `CASAL`/`LDADDAL` with both acquire and release order later loads.
- It becomes possible when an RCpc `LDAPR` follows an LL/SC release write. That is what clang emits for an RCpc target
  without LSE atomics. So the fences are needed on AArch64, and they are sufficient there.
- C++ itself only guarantees this ordering with the seq_cst fences, whatever the target.

## Message passing and multi-thread chains (D-K, generated by `gen.py`)

These tests come from `gen.py` (`python3 gen.py` rewrites them) for the same three codegens. Each family has variants:
the code as it is (`code` or `fixed`), and controls with the ordering removed (`control`, or the code before a fix:
`old`, `old-nodep`). The bad outcome is the `exists` clause.

| Test | Code | Bad outcome | code / fixed | control |
|------|------|-------------|--------------|---------|
| `D-retire-epoch` (3 threads) | skiplist `retire_node`: final level-0 unlink CAS, `retirement_enqueued_` CAS, [fence], `retired_epoch_` read; an epoch advancer; a reader entering in the next epoch | stamp is the old epoch, yet the reader in the new epoch still reads the unlinked node, so it is freed under the reader | `code` Never; `fence` Never (all codegens) | without the `retirement_enqueued_` CAS: Sometimes on llsc-rcpc |
| `E-bitblock-hint` | `lockfree_bitblock_resource`: block construction, `first_block_` CAS, bitmap CAS, hint store vs. hint load and read of the block | reader sees the hint but not the constructed block | `fixed` (release/acquire) Never | `old` (relaxed + address dependency) Never; `old-nodep` Sometimes; `control` Sometimes |
| `F-slot-install` | skiplist `seed_block_generations` (relaxed), `blocks_[idx]` CAS (release) vs. `unpack_ptr` (acquire `blocks_`, then generation) | reader sees the block but an unseeded generation | Never | Sometimes |
| `G-mpsc-regrow` | mp_sc `retire_and_grow`: `buffer_` write, `enqueue_pos_` release store vs. a producer's acquire `fetch_add`, then `buffer_` | producer claims in the new life but reads the old buffer | Never | Sometimes |
| `H-mpsc-ready` | mp_sc slot publication: element, `ready_` (release) vs. consumer `ready_` (acquire), element | consumer sees `ready_` but not the element | Never | Sometimes |
| `I-live-lists` | skiplist slot-block retirement (`blocks_` nulling, fence, `live_lists_` load) vs. a new list (`live_lists_` `fetch_add`, fence, a reader's `blocks_` load) | the retiring list sees one live list while the new list's reader still finds the block | Never | Sometimes on llsc-rcpc |
| `K-iterator-mark` (3 threads) | skiplist `retire_node`: retired mark (relaxed), fence, epoch stamp; an advancer; an iterator's `operator++`: epoch load, snapshot store, fence, mark load | the stamp is the old epoch and the iterator in the new epoch misses the mark, so it reads a node that is freed under it | Never | without the fence: Sometimes on all three codegens |
| `J-block-stamp` (4 threads) | `retire_block` nulls `blocks_[idx]` and pushes (release); `advance_and_reclaim` extracts (acq_rel), [fence], stamps the epoch; an advancer; a reader | as D, for slot blocks | `code` Never; `fence` Never | relaxed push/extract and no fence: Sometimes |

**D and J:** on AArch64 the code is already safe without the new fences, because the acq_rel RMW in between (or the
extract's acquire) orders the stamp's epoch read after the unlink. C++ guarantees that only with a seq_cst fence, so
`retire_node` and `advance_and_reclaim` now issue one before reading the epoch.

**E:** before the fix the hint was safe on AArch64 only because of the address dependency, which C++ does not promise
for relaxed loads.

Limits: the tests cover the instruction sequences around each fence, not whole functions; they model the address-free
core of each pattern (two threads, one word each).
